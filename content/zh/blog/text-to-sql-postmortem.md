# Text-to-SQL 死在哪一天

> VP 没说反对,只说了一句话。

---

> "如果一个 Bert 查询的准但是泛化能力差,而 LLM 泛化能力强但是查不准,你让我做选择,我哪个都不用。"
>
> —— VP

我花了一年才走到能让 VP 对我说出这句话的位置。

走到这一句话面前的时候,我以为我赢了。我们多表查询的准确率从 40% 出头跳到 80% 多,VP 的反馈应该是"什么时候上线",而不是这一句。

我花了三天才听懂他在说什么。听懂之后,text2ontology 的第一原则就出现了。但那是后话。

先讲我是怎么走到 VP 那张桌子前的。

---

## 一、LLM 之前:Text-to-API 的死亡

我加入这家公司之前,这套系统已经在跑了。

它要解决的问题其实可以用一句话讲清楚:**当领导在会议上问一个问题的时候,我们要能立刻回答**。

举一个具体的形状:"X 项目的排期可以往前调吗?"

这个问题本身是简单的,但你回不出来。原因不是会议室太紧张,也不是数据没人收集,而是这一句话**展开后是 N 个子问题**:

- 当前总共有哪些项目?
- 它们的当前排期是什么?
- 排期之间有没有冲突?
- 上下游依赖是什么?
- 谁动谁就阻塞谁?

我所在的域是这样:**几百个并行的项目,每个项目穿过几十张表的依赖图,排期是动态的,变更每天都在发生**。会议上一句"能往前调吗",背后是一次跨 5-10 张表的联合查询加二次推理。没人能在 30 秒内回答。

公司很早就意识到这是个真问题。这套系统在我加入之前就已经在做了 —— 只是当时,LLM 还没火。

当时的策略叫做 Text-to-API:用一个 BERT 模型(LLM 之前的语言模型,擅长"读" —— 分词、分类、相似度,但不会"写",不能生成完整句子;它的天花板是给定一个有限词表,在里面挑出最像的那个)给用户问题分词,分词结果拼成一个 JSON 模板,模板触发预定义的 API 查询,API 返回一张表。

听起来挺漂亮。问题是它**完全没有泛化能力** —— BERT 的天花板就是词表。用户的提问只要中间多一个字母、少一个字母、用了同义词、用了简写,它就识别不出来。

举一个所有人秒懂的例子(不是我们实际的数据,只是问题形状一样):数据库里写的是 "iPhone 14",用户可能问 "苹果14",也可能问 "ip14",还可能打错变成 "iphone4"。这四个全部对应同一行,但 BERT 系统会让其中三个直接 404。

我们的真实数据里全是这种形状。每一类业务对象都有官方写法、口语写法、缩写写法、内部代号写法、历史遗留写法 —— **五份名字指向同一个东西是常态**。BERT 系统每个用户都要先学会"按字典提问",否则没有任何结果。

我们试过用问题改写救它 —— 让 BERT 之前先加一个改写器,把用户的话翻译成 BERT 能听懂的话。单轮问题勉强能跑。但只要加入上下文(用户上一轮问过 X,这一轮的代词指向 X),改写器就崩了。

这条路死在我加入公司之前。

---

## 二、入职第一周:被两堵墙挡住

我加入的时候,ChatGPT 刚火起来。

公司高层的想法是:既然 LLM 看上去什么都能干,那我们之前两年走的路是不是错了?要不要换一条?

我进公司的第一件事,就是回答这个问题。

我们走了两步,得出了一个谨慎的结论:**如果给足够多的、正确的上下文,LLM 是可以在我们的域里推理出有用结果的**。这个结论不强,但够推动一个新项目。这个新项目当时就叫 text-to-SQL —— text2ontology 是很久以后才长出来的下一代,**它存在的意义,是去解决 text-to-SQL 那时回避、甚至根本没办法解决的问题**。但那是一两年之后的事。

新项目从第一天起就撞上了一堵墙。这堵墙有两层。

**第一层是合规层。** 公司数据敏感,所有模型必须本地部署。**任何通过 API 调用的外部模型 —— OpenAI、Anthropic、Google —— 一概不允许**。这意味着我手里能用的最强模型,是当时本地能跑的、量化(把模型权重从 16 位浮点压成 8 位,显存腰斩、精度小幅下降)之后大约 70B(参数数量,比当时 OpenAI 最强的闭源模型小了一个数量级)左右的开源模型,FP8 精度大约占 40GB 显存。这个级别的模型,跟当时 OpenAI 最强的闭源模型完全不在一个量级。所有"如果给足够上下文,顶级闭源模型能做"的乐观结论,放到本地模型上**全部要打折**。

**第二层是数据层。** 好消息和坏消息同时来:

- 好消息:**我们有大量产品数据和销售数据**。结构化、干净、量大。
- 坏消息:**我们没有任何业务知识库**。

在那个年代,所谓"业务知识库"还不是一个有名字的东西。但意思很清楚:**光有数据,系统跑不起来**。因为同一份数据,在不同业务部门眼里有不同的口径;同一个字段,在不同上下文里有不同含义;同一个聚合方式,在不同场景里给的是不同的数。

举个具体的例子:同样是"在售产品数量",销售部门和供应链部门的定义不一样。前者算"过去 30 天有销售记录的 SKU",后者算"当前库存大于 0 的 SKU"。两个查询都对,得出来的两个数字也都对,但放在同一个 dashboard 上,VP 会问:**"哪个是真的?"**

这种问题不是数据问题,是**业务知识没有沉淀**的问题。而当时整个团队、整个域,**没有人把这种知识写下来过**。

所以我从第一天开始,就在跟"两个噩梦"打架:**模型不够强 + 知识没有沉淀**。这两个噩梦合在一起是一种很特别的难度 —— 不是某个具体 bug 那种"找到问题就能修"的难,而是**结构性的、每往前走一步都更深的难**。

## 三、关键词战争

抛弃 Text-to-API 之后,我们转向 Text-to-SQL。思路很朴素:**让 LLM 直接生成 SQL,我们去执行它**。

第一个弯路是把整张表的 schema 塞进 prompt。几张表还好,几十张表的时候 prompt 就爆了。而且 LLM 看到一堆它不认识的字段名(我们的字段命名一半是英文缩写一半是内部代号),会胡乱选字段。甚至**连"准确性"这一层都谈不到** —— 光是把所有相关表的 schema 塞进 prompt 这一步,就已经把当时本地模型的上下文窗口撑爆。SQL 能不能跑通,在这一层之前已经被卡死。

第二个弯路是加上下文。单轮还行,多轮一旦涉及代词指代、隐含约束、对前一轮结果的二次过滤,LLM 就开始编。

但所有这些弯路里,**最致命的不是 schema 也不是上下文,是关键词**。

回到刚才 iPhone 14 那个形状:用户问 "ip14 销量",LLM 生成 `SELECT ... WHERE product = 'ip14'`,数据库返回 0 行 —— 因为数据库里写的是 "iPhone 14"。

LLM 不知道这个映射。schema 里也没有这个映射。**它存在用户脑子里**。

所以我们必须先解决一件事:**用户问的关键词,如何变成数据库里实际存在的值?**

这就是关键词召回问题。它在 2026 年回头看是平凡的,在当时是一座大山。

我们试了三条路。

**1. jieba 分词**(开源中文分词工具,基于词典加统计,不依赖 AI)。速度快、可控、好调试。但它是基于词典的 —— 分得对不对,完全取决于词典里有没有这个词。我们公司的产品命名经常是英文加数字加中文混合,jieba 直接懵。而且更糟糕的是,**对依赖人类经验的问题**(比如"近期"、"重点客户"、"高优先级") —— 这些词 jieba 拆得出来,但拆完没意义,因为它们的含义存在业务知识里,不在词典里。我到现在记得 jieba 把一个产品代号拆成三段的那个下午 —— 终端里那行输出,每一段单独看都是"词",合起来什么都不是。那是我第一次清楚地知道:基于词典的路,在我们这种命名的域里走不到头。

**2. 训练一个 BERT 分词模型**。理论上可行,我们域有大量历史数据。但实操卡在**样本本身的质量** —— 我们部门写在 Excel 表里的示例问题,和用户实际问的问题,**大相径庭**。示例问题是"标准的、合规的、按字典的",用户问题是"口语的、省略的、带歧义的"。用前者训出来的模型,在后者面前完全不工作。加上训练成本和上线流程,我们 PASS 了 BERT。

**3. 用 LLM 做分词加 RAG**(检索增强生成 —— 先去库里捞相关材料,再让 LLM 基于材料回答)。让 LLM 读完用户的问题,直接产出一个 keyword 列表。这是当时唯一能跑通的路。LLM 的语言理解力够覆盖中英文混合、错别字、简写、口语。

走完这一步,**当用户问得相对标准、没有简写没有变体没有错别字、问得很清晰的时候,大功告成** —— 实际并没有。

因为还有一个致命的问题:**LLM 拆出来的关键词,跟数据库里的值,语义上相似,但字面上不一样**。LLM 拆出来 "苹果14",数据库里是 "iPhone 14"。这两个对人是一回事,对 SQL 是两回事。

我们最一开始的策略是把所有可能的关键词都塞给最终生成 SQL 的那一步 LLM,让它自己判断。但效果不好。当时模型局限太大,**你根本不知道是 LLM 没听懂 prompt,还是 prompt 没说清楚**。同一个问题问两次,可能两次的 SQL 完全不一样;甚至同一次跑,温度调到 0,SQL 还是不一样 —— 因为本地模型的实现没那么严格。

于是我们加了**向量召回**(把每个候选词预先算成一串数字,查询时算用户输入的数字,看哪个数字最像 —— 比字面匹配宽容得多)。给每个数据库里的可能值预先算向量,给用户问题里抽出来的每个关键词也算向量,跑相似度,大于阈值的就替换。

这一步开始奏效。"苹果14" 和 "iPhone 14" 在向量空间里距离很近,自动替换;"ip14" 也能命中。只有极少数情况会出问题(比如域内两个真实存在但完全不同的产品在向量空间里太近)。

但这只是治好了**关键词层**的病。整个 Text-to-SQL 的病,深得多。

---

## 四、多表崩塌:那段我感受到绝望的时间

关键词解决了之后,我们以为能往前走。

单表查询确实开始稳定。用户问"X 产品在 Q3 的销量",拿得到。用户问"按区域汇总过去一年的销售",拿得到。这些是单表加一两个聚合,LLM 能处理。

但是当问题涉及到 **3 张表以上**的时候,准确率断崖式下跌。

举一个真实的形状(细节脱敏):"上一个季度我们某类产品在重点区域里的同比变化,跟去年同期相比,排除掉合资品类的影响"。

这个问题展开是:

- 销售表 × 产品表 × 区域表 × 客户表 × 时间表,5 张表
- 一个时间过滤、一个产品类型过滤、一个区域过滤、一个客户类型反过滤
- 一个跟去年同期的对比、一个比例计算
- 最后还要"排除合资品类的影响" —— 这一步需要业务知识(什么算合资品类、影响怎么界定)

LLM 在这种复杂度面前,**写出来的 SQL 看起来对,但 90% 的时候是错的**。错法多种多样:JOIN 关系错,把销售额跟错产品挂上;过滤条件位置错,把"上一个季度"错位到子查询里;聚合粒度错,该 GROUP BY 的没 GROUP BY,该 DISTINCT 的没 DISTINCT。

更糟糕的是,**LLM 一本正经地胡说八道**。

它会给你一个完整的、看起来非常合理的回答:"上一个季度某类产品在重点区域的同比下降了 8.3%。" 数字精确到小数点后一位,看起来无懈可击。你信了。

但你回头去 DB 里手动查同样的口径,真实数字是 11.7%,降幅比 LLM 说的大将近 50%。

更要命的是 LLM 的总结环节经常出错:SQL 算出来的数明明是 11827,LLM 在汇总里写成 11000;让它"保留两位小数",它给你三位;同一个问题问第二遍,它给你的数从 11000 变成 11250 —— 还是没接近真实的 11827。

这不是 bug,是 LLM 的天性。LLM 在 generation 时**不区分"它知道的事实"和"它编出来的合理形状"**。在没有强约束的环境下,它会给你**最像答案的回答**,而不是**正确的回答**。

这个阶段,**整个系统从"AI 数据分析"退化成了"快捷的查数工具"** —— 它能帮你比手写 SQL 快一点点拿到一个数,但你不能信这个数,你必须每个数都回去手动验证一遍。而当你需要验证每一个数的时候,系统的存在价值就归零了。

我那段时间感受到的不是技术挫败,是绝望。

> **数都差不多,凭什么要求用户信任分析?**
>
> 这一年我问得最多的一句。

---

## 五、DeepSeek 与架构 pivot

绝望的同时,DeepSeek v3 横空出世。

我们没法部署完整的 v3,但部署了它的蒸馏版本(蒸馏是用大模型当老师教小模型,得到一个"又小又像大"的版本) —— 具体来说是 Qwen2.5 distill DeepSeek reasoning 32B。公司又给我们加了几张卡。

性能层面,这是当时本地能用的最强思维模型。但光升级模型解决不了根本问题。我们决定**重做架构**。

新架构的核心思路 —— 也是 text2ontology 当前形态的雏形 —— 是这样:

**把数据库本身做元数据化处理**。

具体一点说:对每张表、每一列、每个列的每个唯一值,**预先在数据库以外的一个独立结构里登记一份**。这份登记不是 SQL schema,是更结构化的、可检索的元数据 —— 表是什么、列是什么、列里有哪些唯一值、值跟值之间在业务上是什么关系。

查询的时候,**不再让 LLM 自由写 SQL**。流程倒过来:

1. 用户问问题
2. 分词 —— 抽出问题里的关键候选(产品名、客户名、时间范围、动作动词等)
3. 关键候选 → 向量召回 → 命中数据库里的具体唯一值
4. 唯一值 → 反推它属于哪一列
5. 列 → 反推属于哪张表
6. 几张表确定之后,**表跟表之间的连接关系是预定义的、固定的**
7. 把这一切汇总成一个非常精简的 prompt,**只包含此次问题真正需要的东西**,交给 LLM 生成 SQL
8. SQL 执行,结果回去

这个流程的妙处在于:**LLM 看到的 prompt 非常少,但每一行都非常精准**。之前是把整个数据字典塞给它让它自己挑;现在是我先帮它挑好,只留下相关的。

而且更重要的是:**JOIN 关系是预定义的**。LLM 不再有机会乱选 JOIN。我们预先把"销售表跟产品表用 product_id JOIN,跟客户表用 customer_id JOIN,跟区域表用 region_code JOIN"全部写死。LLM 只需要决定 WHERE 和 GROUP BY,JOIN 它管不着。

结果:**多表联查的准确率,从之前可怜的 40% 出头,跳到了 80% 多**。

代价两个:

1. **非常依赖分词** —— 如果分词把关键词抽错了,后续整条链全错
2. **数据库设计必须够标准** —— 如果 schema 命名混乱、外键缺失、列里塞着多种语义,这个元数据化做出来本身就是错的

但有了这个准确率,我们终于熬到可以跟 VP 演示的地步了。

## 六、VP 那一句话

VP 看完 demo,没有否定路径,也没说"什么时候上线"。

他只说了一句话:

> **"如果一个 Bert 查询的准但是泛化能力差,而 LLM 泛化能力强但是查不准,你让我做选择,我哪个都不用。"**

我当场没接住这句话。**走出会议室、坐车回家的路上,我才意识到他在说第三件事**。

我一直把 BERT 跟 LLM 当成两个 option 在比 —— 哪个查得更准、哪个泛化更好。VP 根本没在 option 这一层跟我说话。

VP 不是在比较 BERT 和 LLM。VP 是在说:**两个都不能用,因为两个都不解决他真正在意的问题**。

他真正在意的问题是 —— 这套系统上线之后,某个高管基于一个错的数字做了决策,**谁负责?**

BERT 不行,因为它查得准但根本回答不了大部分真实问题 —— 80% 的提问会被它直接 404。LLM 不行,因为它能回答大部分问题但 20% 的回答是错的 —— **这 20% 看上去跟另外 80% 完全一样**。从外面看,你分不出来。

VP 不在乎 80% 准还是 90% 准。他在乎的是 80% 准的那一类系统**没法上线**,因为他不知道哪 20% 是错的、也不知道为什么错、更不知道下一次问同一个问题它还会不会错。

我坐车回家的那一路,想清楚了三件事。

**第一件**:VP 是对的。在我们这种零容错的域里,80% 的准确率不是产品,是一个永远要被人复核的草稿。它没有省下任何人力。它只是把"手写 SQL"换成了"读 SQL 改 SQL",还多了一道"我得信任 LLM 吗"的心理负担。

**第二件**:真正的问题不是准确率不够高。是**当它错的时候没有办法定位**。LLM 的天性决定 100% 准确率是不可能的 —— **任何基于 LLM 的系统都会出错,这是不能消灭的事实**。但**"出错时能不能找到"是可以设计的**。这一点之前从没人跟我讲过。

**第三件**:要让"出错时能找到"成为可能,需要两件事:

> 1. **同一个问题,必须产出同一条 SQL** —— 否则一个 bug 没法复现,就没法 debug
> 2. **必须有一套标准的元数据/知识库规范** —— 否则你连"什么是对的"都定义不出来,谈不上找错

这两条结论,就是 **text2ontology 的第一原则**。

## 七、Birth

后来这两条变成了:

**1. 同一个问题在同一个本体下必须产出同一个查询**。这一条最终长成了"两层查询" —— 上层是 Intent(canonical 查询模板),下层是 OD 上的属性。LLM 只填参数,不写 SQL。错的时候,**SQL 是固定的,错只能错在 Intent 选择或参数填充,空间被缩小了一个数量级**。

回想第四节那个多表崩塌 —— LLM 面对 5 张表写 SQL,90% 是错的。本体把这件事彻底改了:**OD 之间的 Link 是组织事先维护好的,不是 LLM 现场推理出来的**。LLM 不再看到 "5 张表",它看到的是 **5 个已经预先连好的 OD 节点**。它只需要在三个**有限集**里做选择:

- 在 OD 网络里挑出本次问题用到的几个 OD
- 在这些 OD 上绑定的 Intent 里挑一个
- 在用户问句里召回几个 Keyword 当参数

这三件事完成之后,**LLM 的工作就结束了**。SQL 由后面的 SmartQuery 引擎顺着 OD 之间的 Link 自动拼出来 —— 一段确定性的后端代码,跟 LLM 无关。我后来才意识到,LLM 在这套系统里根本没机会去拼连接 —— 连接早就被建模 Intent 时钉好了,LLM 也没机会"决定"用哪些表。多表问题不是被 LLM 变聪明解决的,是被**从 LLM 的视野里整体抽走了**。

**2. 必须有一套标准的元数据规范**。这一条长成了 7 个核心概念 —— OD(对象)、OK(知识)、OL(运营事实)、Link(对象间关系)、Causality(因果)、Intent(查询意图)、Keyword(触发词)。每一个都对应一个具体的、之前被忽略的业务知识的形状 —— 每个概念各自负责什么,《设计哲学》那篇里逐一拆解过。

这一天我只看清两条原则。剩下的五条,是之后两年陆续被业务的不同侧面**逼出来**的 —— 每一条都对应另一次"我以为我们解决了,但 VP / 用户 / 数据告诉我们没解决"的小型死亡日。那些故事每一个都值得单写一篇,这里放不下。

---

## 八、回头看,我想留给读者三句话

写完这篇 essay 之后回头看,我想把这一年总结成三句话。

**第一句**:"AI + 数据"这条赛道,前几年所有失败,**根本不是模型不够强造成的**。哪怕把当时全球最强的闭源模型放到我本地跑,这条路也不会通。因为问题在**架构**,不在**算力**。

**第二句**:让 LLM 自由写 SQL,在容错率高的域(toy demo、个人助理、博客小工具)行得通;在零容错的企业域里,从第一天起就不该被允许。**LLM 必须只填参数,不写 SQL**。这是责任能被分摊的前提。

**第三句**:业务知识(口径、定义、命名映射、依赖图)不是 LLM 能"学"出来的,是组织**必须沉淀**的。你不沉淀,LLM 就编一个;LLM 编出来的,在企业域里就是定时炸弹。

而 text2ontology 这个项目,从设计的第一天起,就是为了让组织可以**轻松地沉淀业务知识、轻松地定位错误、轻松地把 LLM 关在它该待的地方**。

它不假装解决了 100% 准确率的问题。它解决的是另一件事:**当它错的时候,你能找到错在哪里**。

VP 那一句话之后,这个赌注我已经下了两年。

我还在押同一个方向。
