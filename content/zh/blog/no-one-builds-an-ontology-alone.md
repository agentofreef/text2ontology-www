# 没有人能独自建成一座本体

> 本体的知识,从来不在一个人的脑子里。所以本体的生产,也不该是一个人的事。

> *No man is an island, entire of itself; every man is a piece of the continent, a part of the main.*
> *—— John Donne,《沉思录·第十七篇》(1624)*

---

我一个人建本体,建了很久。

一开始没什么问题。一个对象、一条关系、一个触发词,亲手一个一个填进去,系统跑起来,答案是对的。我以为这条路我一个人能走到底。

后来发现走不到。一个组织真正在分析的核心概念,大概十个上下:订单、客户、库存、履约、渠道、成本。每一个背后,都藏着一组只有那个领域的人才说得清的事。订单该不该和退款单相连,"金额"是含税还是不含税,管这块业务的人一句话能定,我却要猜半天。再往里,"早单"算不算已发货,做供应链的人心里有数,我只能瞎蒙。

我缺的不是时间,是知识,而这些知识不在我脑子里。它们分散在不同人那里——在做供应链那个人的经验里,在做增长那个人的直觉里,在财务那个人对"成本"二字的较真里。我坐在中间,把他们口头讲的东西转录成本体,转一道,失真一道。

## 把网拆成点,每个点交给一个人

撞过这堵墙之后,出路反而清楚了。

本体是一张网,网上的每个点是一个对象:订单、客户、履约。我原先的错,是想一个人把整张网都建对。可整张网的知识本就不在一个人手里,这件事注定做不成。

换个做法。十个点,找十个人,每人只认领一个,但要认领到底。做供应链的认领"订单"和"履约",做增长的认领"客户"和"渠道",财务的认领"成本"。每个人面对的不再是整张网,只是自己那一个点,任务也收窄成一句话:把我负责的这个点,建到绝对正确。

这一步同时解了两个问题。一个是工作量,没有人需要懂全部,每人只需要懂自己每天打交道的那一块。另一个常被忽略,是职责。当一个点只属于一个人,就没有"这归谁管"的模糊地带:它对不对,只有一个人说了算,也只有一个人要为它负责。职责的清晰不是靠一纸流程规定出来的,是因为这张网被拆成了点,而每个点只有一个主人。

这件事有个更老的名字,叫康威定律:系统的结构,终会长成组织的结构。本体也一样。一个组织的本体,只有长成它自己分工的样子,才可能是对的。

## 写它的人,就是为它负责的人

把"一个点只有一个主人"再往前推一步,会碰到责任落在哪里。

设想另一种分工:本体由一位专职工程师统一来建,各部门口头提供业务定义。听上去合理,但等某个答案出了错,问题就来了——错在哪?是工程师理解偏了,还是业务当初没讲清?两边都拿不出凭据,也都不算存心推诿,真相卡在他们中间,谁也指不出来。这不是人品问题,是责任从一开始就没有一个明确的归属,链条断在了两个人之间。

让认领这个点的人,就是直接为这块业务负责的人,这道缝就不存在了。写"订单"的,是每天对订单负责的那个人;他建的本体准不准,和他业务做得好不好,本来就是一回事。再出问题,直接落到他身上。这里得说清楚,溯源不是为了追责,是为了能改:你知道该找谁、看哪个版本、问哪一次签字。public 让每次发布都带着发布者和版本号,就是为了让这条线一直连着。

所以这一层改的其实不是技术。publish 也好,fork 也好,都只是工具,它们真正动的是谁为哪一块业务真相负责。这是一次职责的重新划分,只是恰好用一套像 git 的东西兑现了出来。

## 本体可以共享,口径不能

十个人各自把自己的点建对了,接下来是流通:A 项目建好的"订单",B 项目要不要从头再建一遍。这是 public 要解决的事。但在讲怎么流通之前,得先分清流通的到底是什么。

**流通的是本体,不是口径。** 这两样东西,用一个简单的标准就能分开:换个场景,它变不变。

"订单"这个对象长什么样——有哪些字段、和谁相连、"金额"指的是什么——在整个组织里是同一个。做履约的人看到的订单,和做财务的人看到的订单,是同一张表、同一组字段,不随场景改变。这样的东西,值得建一次,所有人共用。

口径不是这样。同样问一句"早单率是多少",做履约的人要的和做财务的人要的,根本不是一个数;就算同一个人,这个月盯渠道、下个月盯库存,口径也跟着变。同一个问题,在不同场景下有不同的答案,而且每个答案在它自己的场景里都对。这不是因为大家没对齐,是这个问题本就没有一个脱离场景的标准答案。

想清楚这点,"把口径统一成全公司标准"就站不住了。你就算真统一了,也不过是挑了某一个场景的答案,强加给所有别的场景,统一不掉的东西,硬统一只会失真。所以口径留在它该在的地方,在使用它的那个人、那个场景手里;而本体,因为它在所有场景下都一样,才被抽出来共享。

公共市场保证的,是你拉到的那个"订单"是对的。至于在这个订单上算什么、怎么算,是你自己的事。地基统一,房子各盖各的。

## 把 git 搬到本体上

分清了共享什么,剩下的是机制,而这套机制软件工程六十年前就有了现成的:git。代码也一度是一个人抱着一份文件改,直到 git 把协作变成基础设施——发布、拉取、追上游、提合并。

public 把这套东西原样搬到了本体上:

| git | public ontology | 做的事 |
|---|---|---|
| `push` | publish | 把建到绝对正确的对象发布到公共目录,一次,有归属,有版本 |
| `fork` | fork | 别人按需把它拉下来用,得到一份只读副本 |
| upstream | lineage + "有更新" | 上游发了新版,下游自动看到提示,可一键采纳 |
| Pull Request | proposal | 下游把改进提回上游,由负责人评审、合并 |
| history | version | 每次发布是 append-only 的一版,带 diff 和说明 |

有几处是特意这么设计的。发布出去的只有人写的语义字段,数据源配置和连接凭证在入库前就剥掉了——你共享的是"订单长什么样",不是数据库密码,也不是你怎么算早单率。拉下来的副本是只读的,要改,回自己的源头改,再走 proposal 提上去。而这一整套,LLM 不碰一个字节:它是已授权字段的搬运,不是生成。人负责真相,机器只在确定的轨道上搬。

## 冷启动变成了另一道题

这一步把冷启动整个改写了。

过去一个新项目面对的是一座空本体,第一个有用的答案要等几周。现在它面对的是一个已经有人把每个点建对、也验证过的公共目录。按这次要分析的东西自选拉取——不同场景用到的点本就不一样多——拉一个现成的、对的"订单"下来,在它上面长自己的口径。

而且它会越用越值钱。多一个建对的公共对象,下一个人的起点就高一截;被越多项目拉取、越多 proposal 打磨,它越准。复利不再发生在一个人的本体里,而是发生在整个组织的目录里。

这也顺带回答了那个常被问到的问题:大公司会不会把它抄成一个 feature?会。publish、fork、proposal 这些机制是代码,谁都能抄。抄不走的是目录里那些被懂行的人建到绝对正确、又在真实提问里验证过的本体,和那张谁为哪个点负责的网。git 是开源的,GitHub 不是;不可复制的从来不是 git,是上面的仓库和人。本体的护城河也在这里。

## 它是组织内部的公共,不是跨企业的超市

最后要划一条线,否则"public"迟早被用滥。

这里的 public,是一个组织内部的公共:跨项目、跨团队、跨人,但不跨企业。这不是保守,是本体的性质决定的。本体贴着某一个组织的业务长出来。做电商的"订单"和做 SaaS 的"订阅"是两个本体;就算都叫"客户",两家公司底下连的也是完全不同的业务。

所以指望一个跨企业的"本体超市",像装 npm 包一样下别人的本体,是误会了本体是什么。一个对象的价值,正来自它和某个组织的业务咬合得有多紧;一旦要它通用,它就不再精确,也就不再可信。public 真正有用的地方,是让一个组织内部那些分散在不同人手里的本体彼此发布、复用、校准。在这条线之内,它是纯粹的增益;越过这条线,它就开始违背本体存在的理由。

## 尾声

我一个人建本体,建了很久。这套系统真正活过来的那一刻,是它不再需要我一个人建的时候。

本体不是一个聪明人的作品,是一个组织的共识。网上没有一个点是孤岛,每个点都是整张网的一片。一个人能把一个点建到绝对正确;要把整张网建到绝对正确,靠的不是更聪明的人,是让每个点都由最该为它负责的那个人来建。至于在这张对的网上各自算什么、怎么算,那是各人自己的事,本就不必统一。

我们要统一的,从来只是那张网本身。
