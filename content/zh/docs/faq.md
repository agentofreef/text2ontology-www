# 开始之前

> 诚实的预期:这不是黑盒魔法,以及上手前值得先想清楚的四个问题。

---

## 一句实话

大多数「AI agent + 你的数据库」产品有一个没说出口的假设:**schema 元数据 + 一个 LLM 就够回答业务问题了。** 我们花了很长时间在不同形态、不同技术栈上试图让这条路走通,每次都以同样的方式崩掉。

**Schema 不携带含义。** `INFORMATION_SCHEMA.COLUMNS` 不知道「早单」在你公司是 `status='CONFIRMED'`、在别家是 `IN ('CONFIRMED','SHIPPED')`;不知道 Q1 的截止是 14 号不是 15 号;不知道 2025 迁移后哪些客户被错分类了。这些活在人脑里、审计历史里、没人写下来的例外清单里——光盯着列名的 LLM 找不回来。

所以这套系统是常规卖点的**反过来**:**组织慢慢积累一套人工策展的本体,AI 只是去读它。** 不是自动学习。更贴切的类比是**给新分析师做 onboarding**——一个一旦你解释过、就不会忘的分析师。

## 上手前值得先想清楚的 4 个问题

不是硬性要求,系统照样能起。但这是最容易撞墙的地方。

1. 你的业务到底在做什么?你想从 AI 分析里得到什么是今天得不到的?
2. 数据源有多干净?有没有迁移到一半的列、断掉的外键、拖了两个季度想修的东西?
3. 你愿不愿意花时间把基础写下来——「早单」是什么意思、哪个字段定义「核心客户」、Q1 截止点在哪?
4. 团队脑子里的知识(定义、例外规则、校准说明)有没有写在某个共享的地方?

如果这几个都觉得模糊,那通常就是**最该从那里开始**的地方——不是因为系统要求,而是因为时间都花在那儿。

## 常见问题

### 它和 Text2SQL / "AI 聊数据库" 有什么不同?

Text2SQL 让 LLM 直接写 SQL,错误无界、不可定位、不可复现。本体路径让 LLM 只从有限集里挑、填参数,SQL 由确定性引擎拼——错误有界、可定位、可复现。详见 [介绍](/zh/docs/introduction/)。

### 它准吗?

它不承诺「一次就准」。它承诺的是**一致**(同问题同答案)和**可纠**(错误有地址,修一次永久生效)。准确率是**积累**出来的,不是模型一次给的。

### 数字会不会被编造?

不会。LLM 在工具链里从不写数字,只发结构化指针,由机械层解析成真值。详见 [查询模式](/zh/docs/query-mode/)。

### 比传统 BI 重在哪?

你要 curate / annotate / activate,不会十五分钟开箱即用。换来的是「一旦修对就保持对」。详见 [纠错飞轮](/zh/docs/correction-flywheel/)。
