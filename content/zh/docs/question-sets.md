# 第 3 步 · 问题集

> 定义衡量成败的『正确答案』,跑通第一遍,以及为什么分词是你第一个要检查的东西。

---

数据接好了、本体建好了,怎么知道系统到底跑得对不对?靠**问题集**。

> 问题集是衡量整套系统是否成功、以及如何衡量"事实标准"的**关键指标**。

## 先想清楚:它其实是你给数据分析补的那台「预言机」

回到[介绍](/zh/docs/introduction/)里那条核心信念——**数据分析没有天然的预言机**。写代码能越改越对,是因为测试套件就是预言机:跑一遍、通过/失败、迭代。数据分析里本来没有这个东西,所以模型永远停在 demo。

问题集就是你**亲手造的那台预言机**。它和工程师写的测试套件是同一种东西:你把"这个问题,在我们组织的共识里应该得到什么"写下来,系统就第一次有了一个**可以反复对照**的标准。第 2 步是把"概念是什么意思"立法,这一步是把"什么算对"立法——同一种功夫,只是换了个对象。

## 它在系统里长什么样

在系统里,问题集对应 **Agent → 数据集测试**(`/ontology/lakehouse-agent/dataset-testing`)。UI 里的正式叫法是「**数据集测试 / 测试集**」,结构有三层,值得分清:

| 层 | 是什么 | 关键点 |
|---|---|---|
| **测试集**(suite) | 一组用例的命名集合 | 一个场景一套,比如「销售场景 v1」 |
| **用例 / 问题**(case) | 一条自然语言提问 | 可以挂一个**参考答案**(组织共识下应得的结果,人写的事实标准) |
| **版本运行**(Run) | 对整套用例的一次执行 | **绑定一个具体的 LLM 配置**,可命名、可对比 |

这里有一个容易被忽略、但很要紧的设计:**一次运行是把每条问题"忠实重放"一遍**——走的是和线上提问**完全相同**的那条路(强制分词 → 三级召回 → 只有 `lookup` + `smartquery` 两个工具,SmartQuery 引擎拼 SQL)。所以一次测试不是另写一套验证逻辑,而是**线上那次提问的复刻**。它测的就是用户真正会遇到的东西。

每条用例跑完,系统都会留下现场:每一轮工具调用、`generated_sql`、执行结果、最终答案、耗时 / 模型 / token。**这份现场,正好就是出错时你要看的全部线索**——测试和调试在这里是同一块面板。

## 怎么判对错——以及为什么这么判

这一步最反直觉:**系统不自动判分。** 一条用例跑完,默认是「待判定」。判定有两条路:

| 判定方式 | 怎么做 | 适合 |
|---|---|---|
| **手动** | 你看一眼答案,点「正确 / 错误」 | 量小、或你想亲自把关 |
| **AI 判定** | 一个 LLM 评审,拿最终答案去对照你写的**参考答案**(并喂给它和线上 Agent 同一份召回上下文,好判断语义是否等价),给出 正确 / 错误 / 不确定 | 量大、想批量过一遍 |

**为什么不直接自动算个分?** 因为回到那条信念:业务问题是**欠定的**,"对"意味着"和组织共识一致",不是和某个客观真值一致(见[介绍](/zh/docs/introduction/)"卖的是一致性,不是正确性")。既然"对"是被共识**指定**出来的,那"判对错"这件事本身也得有人立法——要么你亲自判,要么交给一个**受你约束、手里拿着你那份参考答案**的评审。系统不会假装存在一个它其实没有的客观分数。这正是它和"给你蹦个准确率就完事"的工具最根本的区别。

## 版本对比:你能亲眼看见那个棘轮

问题集真正的力量,在**多个版本之间**才显出来。

改了本体、口径或分词之后,**重跑一个新版本**,再用 **N 路对比**(compare)把两次运行并排摆开,逐题看差异。因为每个版本都**绑死了它当时用的 LLM 配置**,你能干净地把两件事分开:这次变好/变坏,是**你改的本体**带来的,还是**只是换了模型**带来的——这在"AI 聊数据库"那套黑盒里是根本分不清的。

更要紧的是:上个版本被你修对的题,在下个版本里**依然对**。那条"修一次、就不再回退"的棘轮,你不是凭感觉相信它,而是在对比视图里**一格一格看得见**。

## 跑通第一遍

1. 把问题集放进系统(可以手动加,也可以 CSV / Excel 导入)。
2. 建一个版本,跑一遍。

**跑之前,心里要有一个预期:第一遍效果大概率不好。** 原因很简单——**大语言模型八成还不理解你这个问题里那些特定关键词是什么。**

所以这时**先不要盯准确率、也先别急着判对错**。第一遍跑完,你该做的是去**检查分词**(见下),确认系统有没有"看懂"你问的词。分词都对了,再跑第二个版本——这回准确率会比第一遍**高得多**。

## 为什么先查分词

整套系统里,**分词(tokenization)是命门**:超过 60% 的环节都依赖它。

分词的核心逻辑是:**用大语言模型,解释你这个问题里实际涉及到的关键词是什么。**

当 LLM 能正确把这些关键词抽离出来,系统和 Agent 就能更好地理解它们;**通过这些关键词,系统再反推出你问题对应的本体(OD)和本体的属性。** 关键词错了,后面全错。

去哪看分词:

- **Agent → Token 召回**(`/ontology/lakehouse-agent/token-recall`)—— 复现"这句话被怎么分词、召回到了什么"。
- **知识工程 → 关键词分诊**(`/ontology/lakehouse-keyword-triage`)—— 修分词:补缺词、纠错别名、调指标优先级。

> 小贴士:每跑一条用例,它的分词都会沉淀成一条**标注**(`/ontology/lakehouse-agent/annotations`)。把对的标注**确认**下来,它会作为 few-shot 反哺下一次分词——这是问题集让系统"越用越准"的一条暗线。

## 跑通之后

到这一步,整套系统基本就能跑起来了。剩下的,是把"运行 → 判定 → 找到错的那条 → 就地修 → 重跑对比"变成一个习惯——也就是[调试循环](/zh/docs/correction-flywheel/)。问题集给了你**入口**(哪几道错了),调试循环告诉你**每道错的地址在哪、怎么修一次就不再回来**。
