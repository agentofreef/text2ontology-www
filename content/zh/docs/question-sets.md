# 第 3 步 · 问题集

> 定义衡量成败的『正确答案』,跑通第一遍,以及为什么分词是你第一个要检查的东西。

---

数据接好了、本体建好了,怎么知道系统到底跑得对不对?靠**问题集**。

> 问题集是衡量整套系统是否成功、以及如何衡量"事实标准"的**关键指标**。

## 问题集是什么

它没有想象中复杂。问题集其实就是一组对应关系:

> **一个"正确答案" ↔ "正确答案的实例示例"。**

也就是:对一类提问,组织共识下**应该**得到什么结果(正确答案),配上一个具体的例子。这一步本质上是把"什么算对"写下来——和[第 2 步](/zh/docs/builder-mode/)里把"概念是什么意思"写下来,是同一种功夫。

在系统里,问题集对应 **Agent → 数据集测试**(`/ontology/lakehouse-agent/dataset-testing`):你建命名的测试套件、后台批量跑、看 run 与 run 之间的 diff。

## 跑通第一遍

1. 把问题集放进系统。
2. 跑一遍。

**跑之前,心里要有一个预期:第一遍效果大概率不好。** 原因很简单——**大语言模型八成还不理解你这个问题里那些特定关键词是什么。**

所以这时**先不要盯准确率**。第一遍跑完,你该做的是去**检查分词**(见下),确认系统有没有"看懂"你问的词。分词都对了,再跑第二遍——这回准确率会比第一遍**高得多**。

## 为什么先查分词

整套系统里,**分词(tokenization)是命门**:超过 60% 的环节都依赖它。

分词的核心逻辑是:**用大语言模型,解释你这个问题里实际涉及到的关键词是什么。**

当 LLM 能正确把这些关键词抽离出来,系统和 Agent 就能更好地理解它们;**通过这些关键词,系统再反推出你问题对应的本体(OD)和本体的属性。** 关键词错了,后面全错。

去哪看分词:

- **Agent → Token 召回**(`/ontology/lakehouse-agent/token-recall`)—— 复现"这句话被怎么分词、召回到了什么"。
- **知识工程 → 关键词分诊**(`/ontology/lakehouse-keyword-triage`)—— 修分词:补缺词、纠错别名、调指标优先级。

## 跑通之后

到这一步,整套系统基本就能跑起来了。剩下的就是回到调试循环里持续校准。完整的调试决策树(分词 → OD → 描述 → 表/SQL/主外键)见 **[调试循环](/zh/docs/correction-flywheel/)**。
