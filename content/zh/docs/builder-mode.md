# 第 2 步 · 本体建模

> 把业务概念映射到数据:每个概念是一个 OD,维度是属性,关系是 Link,每个 OD 背后一张语义表。

---

这是整套配置里最核心的一步,也是**业务人员和技术人员要坐到一起**的地方。要回答的问题其实很朴素:

> 在当前这个场景下,你具体想分析的**业务概念**有哪些?用什么**数据**来描述这些概念?每个概念有哪些**维度**?概念和概念之间是什么**关系**?

> **⚠️ 当前请优先手动构建本体。** Builder(构建)模式还**不可靠**——它能帮你起草,但经常需要大量返工。**推荐的路径是:在「本体」页面(`/ontology/lakehouse-objects`)手动定义 OD / semantic_sql / 属性 / Link / 描述**,并优先用手动方式查询验证。把 Builder 当成一个可选的"草稿助手",而不是依赖它一键建好。

## 业务概念怎么映射进系统

把上面的业务语言,翻译成系统里的对象:

| 业务语言 | 系统对象 | 数据层对应 |
|---|---|---|
| 一个业务概念 | 一个**本体 OD** | 一张表 |
| 概念的一个维度 | 本体的一个**属性 Property** | 表的一个列 |
| 概念与概念的关系 | 一条 **Link** | 表与表的主外键 / 关联键(join key) |

也就是说:**每个本体就是一个业务概念,本体的属性就是这个概念的维度,本体之间的关系就是概念之间的连接。**

## 每个本体背后是一张"语义表"

站在数据层,**每个本体(概念)对应一张表**。这张表可以简单理解为传统 BI 里的**语义层(semantic layer)**——每个语义层都对应一条 SQL,这条 SQL 就是本体的 **`semantic_sql`(描述 SQL)**:你用它来**描述本体对应的数据**。

- 本体对应的表 → 本体本身
- 表的列 → 本体的属性
- 表与表的主外键关系 → 本体与本体的 Link

> 一个本体对应**恰好一条** `semantic_sql`,而这条 SQL 可以引用任意多张物理表。物理表是实现细节,本体是业务封装。

## 给每个列判断语义(Machine Code)

写完 semantic_sql、连好关系之后,你要**逐列判断:这个列有没有语义**。

- **有语义** → 不用管(它能作为维度/关键词被理解)。
- **没语义** → 例如机器码、时间戳、手机号、各种乱七八糟的机器编码,它们本身不承载业务含义 → **勾上 `Machine Code` 选项**。

标了 Machine Code 的列不会被当成有意义的维度去召回/理解,避免污染。

## 用自然语言描述本体和列(= 运行时的提示词)

数据接好、关系连好、机器码标好之后,还有关键一步:**用自然语言描述每个本体、以及本体的每个列到底是什么意思。**

- 你就用大白话写:这个本体代表什么业务对象、这个列代表什么维度、有没有口径上的注意点。
- 在系统实际运行时,**这些描述就相当于喂给 Agent 的提示词**。"列名告诉机器,描述告诉 AI"——名字不重要,意义才重要。

写到这里,数据和数据的准备就基本 OK 了。当存在**多个业务概念**时,记得把这些表之间的关系(Link)关联起来。

## 本体怎么"切":概念融合策略

"本体"这个概念坦率讲比较抽象。建本体时,**以业务的形式去理解到底有哪些本体**,而不是照着物理表一张张搬。

一个实用原则:**如果可能,把对应数据库里相关的概念融合成一个本体(一个维度统一考察)。**

> 比如"**盈利**"这个概念。谈盈利,它有**毛利率**和**净利率**。最佳策略是把它们放在**同一个本体**里统一考察——而不是一上来就拆成两个。

什么时候才拆成两个本体?**当一个统计口径无法同时覆盖**时。比如用户的提问里**同时涉及毛利润和净利润**、而它们的口径无法在一个本体里统一,那就写成两个本体。

> 经验法则:**先尝试融合,口径冲突时再拆分。** 概念过度拆分会让本体网络变碎、Link 变多、召回变难。

## 怎么建:优先手动,Builder 仅作辅助

**推荐手动构建。** 在 **数据资产 → 本体**(`/ontology/lakehouse-objects`)里手动定义 OD、写 `semantic_sql`、配属性、连 Link、填自然语言描述。这条路最可控,也是目前**最可靠**的方式。

**Builder(构建)模式当前不可靠**,只在你已经清楚要建什么、想让它帮忙起草初稿时再用:

- 打开 **Agent → 湖仓 Agent**,切到 **构建(builder)模式**,用大白话把上面这些讲给它。
- 它是**访谈式**的:有一个 **≥3 轮访谈门槛**才开始提议。
- 它产出的都是**草稿(`mark=false`)**,**必须人工逐条审阅并激活**才生效。**激活前一定要读一遍——它经常出错,别一键照单全收。**

## 三条硬不变量(激活时绕不过去)

1. **OD 必要性**:没有 active 的 OD,查询工具拒绝执行。
2. **OD 1:1 semantic_sql**:每个 active OD 恰好一条 SQL 定义。
3. **无孤岛 OD**:多个 active OD 之间必须通过 active Link 相连,不能有孤岛。

建完模、激活后,进入 **[第 3 步 · 问题集](/zh/docs/question-sets/)**。
