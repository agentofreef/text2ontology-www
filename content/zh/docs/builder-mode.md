# Builder 模式:为业务建模

> 用大白话把业务讲给 Agent,审阅草稿本体,激活它。

---

数据接进来之后,本体还是「草稿级」的。打开 **Agent → 湖仓 Agent**,切到 **构建(builder)模式**,用**大白话**把你的业务讲给 Agent 听。

## 它怎么工作

- Agent 是**访谈式**的:它会反复追问澄清,有一个**≥3 轮访谈门槛**才会开始提议建模——这是为了逼出脑子里的隐性共识,不是流程繁琐。
- 它产出的 OD / 指标 / Link 都是**草稿(`mark=false`)**,**必须人工激活**才生效(`mark=false → 人工 activate` 生命周期)。
- **激活前一定要读一遍**。

## 一个判断标准

如果你没法跟同事解释清楚「为什么要有这个 OD / 这个指标」,那通常说明业务侧的共识还没谈拢——这才是该停下来的地方,而不是急着激活。

> 这套「AI 提议 → 人工激活」的模式,就是 Palantir Foundry「分支 / 提案」流程的同构简化版。

## 在哪查看本体

可以在 **数据资产 → 本体**(`/ontology/lakehouse-objects`)查看 / 管理 OD 和它们的属性图。

记住三条硬不变量(见 [核心概念](/zh/docs/core-concepts/)):**至少要有一个 active OD;每个 active OD 恰好一条 semantic_sql;多个 active OD 之间不能有孤岛(必须通过 active Link 相连)。** 这些由架构强制,激活时绕不过去。

建完模、激活后,就可以 **[提问](/zh/docs/query-mode/)** 了。
