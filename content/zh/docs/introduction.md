# 介绍

> text2ontology 是什么、解决什么问题,以及那条解释一切设计的核心信念。

---

## 一句话

**text2ontology 把「自然语言提问 → 数据分析」做成一件可问责的事。**

它的根本主张只有一句:

> **不让大模型自由生成可执行查询(SQL / DAX / Pandas / 任何 DSL)。** 大模型只在「组织维护好的指标模板」里**填参数**;真正的可执行 SQL 由一个**确定性编译器**(SmartQuery 引擎)沿着预先定义好的本体关系拼出来。

由此带来的那个**唯一卖点**是:**当 AI 答错时,每个错误都有一个「地址」**——是哪个指标、哪个别名、哪条因果边出了问题。你打开那一行、改一次、以后同一类错误不再出现。这不是「换个更大的模型」能给你的东西。

它面向的人:**已经试过 Text2SQL / "AI 聊你的数据库",并且看着它在列名别名、KPI 歧义、"这答案到底对不对" 上反复崩掉的人。** 如果你想要一个开箱即出魔法答案的黑盒,这套系统大概率不适合你——这一点我们说得很直白。

## 为什么这样设计

理解下面三点,后面所有界面和操作才讲得通。

### 1. 数据分析没有「预言机」(Oracle Problem)

AI 写代码能收敛,是因为**测试套件就是预言机**:写代码 → 跑测试 → 通过/失败 → 迭代。

**数据分析里没有这个东西。** 你问「我们的早单率是多少?」,模型答「12.3%」,你**没有任何自动机制**能验证 12.3% 对不对——因为「早单」到底是 `status='CONFIRMED'` 还是 `status IN ('CONFIRMED','SHIPPED')`,这个共识只活在人的脑子里,不在任何代码或数据里。

> 没有预言机 → LLM 无法迭代收敛 → 永远停在 demo,做不成产品。
> 这是**数学上的限制**,不是模型能力问题,换更大的模型也救不了。

我们的解法:**既然没有天然预言机,那就让组织人工造一个语义预言机——这个预言机就是「本体(Ontology)」。**

### 2. 卖的是「一致性」,不是「正确性」

「早单率是多少」这种业务问题本质上是**欠定的**:早单 = 确认/已付/已发?分母 = 触达客户/新客户/目标客户?每种组合都对应一个真实的数,**没有哪个是「唯一正确答案」**,每个都是解集里的一个解。

本体做的不是 Discovery(发现真理),而是 **Resolution(指定共识)**:在合法的解里选一个作为组织标准,锁定它,让以后**同一个问题永远得到同一个答案**。

> 当答案「错」了,它不是「客观错误」,而是「和当前共识不一致」→ 改本体,所有未来查询同步被纠正。
> **这套系统真正卖的,是「可治理的组织共识」,不是「更聪明的 AI」。**

### 3. 有界错误 ≠ 无界幻觉

这套系统不声称永不出错。它声称它的**错误模型和 LLM 幻觉是两个物种**:

| 维度 | Text2SQL(LLM 直接写 SQL) | text2ontology(本体路径) |
|---|---|---|
| 错误空间 | 无界——任何看似合理的 SQL | 有界——只能来自 `别名 ∪ 指标优先级 ∪ 因果` 这个有限集 |
| 能否定位 | 不能(LLM 是黑盒) | 能,精确到哪一层召回、哪个 keyword |
| 怎么修 | 改 prompt,影响未知 | 改一行数据,影响有界,所有未来查询一起被修好 |
| 可复现 | 不可复现(LLM 非确定性) | 完全可复现(固定本体快照 → 固定 SQL) |

> **有界错误是可接受的错误;无界幻觉不是。**
