# 配置流程与协作分工

> 三步配置法——数据源、本体、问题集——以及业务人员与技术人员如何分工协作。

---

把一套 text2ontology 跑起来,本质上是三步:

1. **数据源准备** —— 把数据正确接进来。
2. **本体准备(业务逻辑准备)** —— 把"这个场景到底要分析哪些业务概念、用什么数据描述它们"落成本体。
3. **问题集准备** —— 准备一组"正确答案",用来衡量系统到底跑得对不对。

这三步里,第 2 步是核心,也是唯一需要**业务人员和技术人员坐到一起**的地方。先理解谁负责什么,后面一切都顺。

## 谁负责什么(协作分工)

一句话:**业务人员负责"意义",技术人员负责"数据管道",自然语言描述是两者之间的桥。**

| 步骤 | 业务人员负责 | 技术人员负责 |
|---|---|---|
| **1 数据源** | 说清楚有哪些数据、来自哪里 | 连接 + 配置数据源(PBIX / PBIT / Excel / Postgres / SQLite) |
| **2 本体** | 这个场景有哪些**业务概念**、每个概念有哪些**维度**、概念之间什么**关系**;以及——**每个概念和每个维度到底是什么意思**(自然语言描述) | 把每个概念映射成**一张表 + 一条 semantic_sql**;维度映射成**列**;关系映射成**主外键 / join key**;给无语义的列(机器码、时间戳、手机号)标 **Machine Code** |
| **3 问题集** | 定义"**正确答案**"——即组织共识下,这个问题应该得到什么(事实标准) | 把问题集灌进系统跑、读分词、走调试循环 |

> 这正是["业务本体工程师"](/zh/blog/business-ontology-engineer/)这个新角色的来由:第 2 步需要一个既懂业务、又能和技术对齐的人。小团队里,这可能是同一个人;大团队里,这是业务和技术围着本体的一次对话。

## 三步速览

### 第 1 步:数据源 → 完成的标志

把数据正确接进来、连接配置完成,第 1 步就结束了。所有接入都走 collector-server 一个入口,接好后数据源状态变 `ready`。详见 **[第 1 步 · 接入数据源](/zh/docs/data-sources/)**。

### 第 2 步:本体 → 把业务讲成数据

这是核心。你要回答:这个场景具体想分析的业务概念有哪些?用什么数据来描述这些概念?每个概念有哪些维度?概念和概念之间是什么关系?

映射到系统里:

- **每个本体(OD)= 一个业务概念**
- **本体的属性 = 业务概念的维度**(站在数据层 = 表的列)
- **本体与本体的关系 = 概念与概念的连接**(站在数据层 = 表与表的主外键 / 关联键)
- **每个本体对应一张表** —— 可以理解为传统 BI 的**语义层(semantic layer)**,每个语义层对应一条 SQL(`semantic_sql`,即"描述 SQL"),你用这条 SQL 来**描述本体对应的数据**

落地后还有两件事:给每个列判断**有没有语义**(没语义的标 Machine Code),以及用**自然语言描述**每个本体和每个列是什么意思(运行时它就相当于 Agent 的提示词)。

> **提示**:Builder(构建)模式当前**不可靠**,建议**优先手动构建**本体。

详见 **[第 2 步 · 本体建模](/zh/docs/builder-mode/)**。

### 第 3 步:问题集 → 衡量成败的事实标准

问题集没那么复杂,它其实就是一组"**正确答案**"和"**正确答案的实例示例**"的对应。它是衡量整套系统是否成功的关键指标。

灌进系统跑第一遍时,**心里要有预期:第一遍效果大概率不好**——因为 LLM 八成还不理解你问题里那些特定关键词。这时不要先盯准确率,而是先去**检查分词**。详见 **[第 3 步 · 问题集](/zh/docs/question-sets/)** 与 **[调试循环](/zh/docs/correction-flywheel/)**。

## 心态:第一遍不准是正常的

整套系统的智能是**积累出来的**。配置完成只是起点;真正让它变准的,是回到调试循环里,**一遍遍校准分词、本体和描述**。先查分词,这一步决定了 60% 以上的成败。
